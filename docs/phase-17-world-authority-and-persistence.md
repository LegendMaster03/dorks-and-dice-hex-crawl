# Phase 17 — world authority and persistence contract

**Status:** Phase 17 shipped and the deployed tester database was upgraded transactionally to schema 10. The one-time schema-8/9 conversion and cutover scripts were subsequently retired; current deployments retain the general PostgreSQL migration framework and default to fresh schema-10 initialization. Existing hex world compatibility remains part of the runtime until later phases retire it.

## Authority and identity

- **Ruleset/procedure**: immutable, revision-pinned `tilingDsSymbol` declares the structural requirement. It does not specify physical world geometry. This field is neither replaced nor rewritten.
- **World**: either a validated `PeriodicWorldTiling` (topology witness, world-coordinate metric witness, explicit optional physical-distance calibration, translation basis, pose, stable ID and revision) or a pre-existing `HexGridDefinition` that is projected through `LegacyHexTilingCompatibility`. There is no extra pattern implementation catalog, image prerequisite, or Surveyor write path.
- **Source map**: separately stores asset key, affine/projective registration and coverage. Raster observations cannot modify world topology/geometry.
- **Semantic layers**: features, locations, source maps, environment annotations and player knowledge retain their own identities and coordinate/ownership semantics; polygon intersections use actual boundaries.
- **Cell identity**: `WorldCellId(tilingId, PeriodicCellAddress(motifCellId, LatticeDisplacement(U,V)))`. The motif ID and translation basis are part of the address convention. Topology or translation-basis changes must never reuse the same identity/revision while silently reinterpreting existing cell addresses.

World-authored generalized geometry must pass `PeriodicTopologyWitness.ValidateAdjacency()` and `PeriodicMetricWitnessValidator.Validate()` before persistence. Structural validation proves the claimed translation-cover incidence and primitive lattice; metric validation proves concrete polygon embedding and constraints within bounded limits. The D-symbol alone cannot substitute for the metric witness.

`PeriodicWorldTiling` exposes `Resolve`, `Boundaries`, `Reciprocal`, `Neighbors`, `Containing`, `Nearby`, `Intersecting`, and calibrated `MeasurePhysicalDistance`. Containment uses scale-aware collinearity tests, so sufficiently small valid motif cells are not falsely reported as ambiguous. Its final shared-edge and vertex classification also bounds rounding uncertainty from the *absolute* world-coordinate representability of the supplied points, separately by axis; a boundary returned near a large world origin must not be classified confidently as belonging to only one incident cell merely because its rounded midpoint lies a few representable spacings from the exact geometric line. This does not restore the former fixed-area tolerance that incorrectly captured small-cell interiors. Lookup handles polygon-boundary ambiguity explicitly; region enumeration is inverse-lattice bounded with a configurable hard ceiling of 100,000 candidate cells. Interfaces are atomic; multiple interfaces may refer to one geometric polygon side, so movement must not assume whole unsplit sides. The inverse-lattice candidate prefilter projects motif footprints in local coordinates (never adding and subtracting the world pose), with conservative rounding allowances derived from world-coordinate magnitude and lattice scale; actual polygon predicates still decide final membership. Enumeration does not materialize an infinite plane.

## Existing-hex identity and compatibility

Existing `HexGridDefinition.Id` and `OverworldDefinition.Id` are retained. A legacy axial `HexCoordinate(Q,R)` corresponds bijectively to `PeriodicCellAddress("hex", (Q,R))`. The old `HexId` maps to `WorldCellId` with the **same grid UUID**. The translation basis, polygon corners, physical units, rotation and origin are derived from the actual persisted grid by `HexGeometry`, not generated anew from a superficially equivalent canonical D-symbol. This preserves pointy/flat orientation, map-coordinate scale, world pose and physical cell positions. **Map/world coordinates and physical travel distance are distinct quantities**: the realized legacy polygons and basis use `world-unit` coordinates without rescaling source-map alignments, world features, or semantic positions. The optional persisted `PhysicalDistancePerWorldUnit` is a complete `DistanceMeasure` (value and `DistanceUnit`, including custom conversion metadata), derived from the legacy declared neighbor-center distance divided by the actual world-coordinate center separation (`sqrt(3) * HexRadiusWorldUnits`). `MeasurePhysicalDistance` applies this conversion; generalized worlds lacking calibration do not silently infer real-world distances from coordinate units. The legacy compatibility validator checks pose, translation vectors, local polygon vertices, and the physical calibration independently using cell-scale tolerances rather than absolute-origin-based tolerances. The legacy metric bridge constructs its polygons and lattice vectors from a zero-origin copy of the saved grid before applying the persisted world origin, avoiding catastrophic cancellation at large finite coordinates. Legacy `HexTraversalState`, directional intent, entry/last direction, progress, pending encounters, events, player knowledge and procedure snapshots remain in their existing representations until Phase 18 provides equivalent generalized movement.

`OverworldDefinition.Grid` is a temporary compatibility accessor for hex-only consumers. New generalized worlds have `Tiling` and no Grid. Attempting to use the hex runtime for generalized geometry is blocked; Phase 18 must remove this dependency after migration and replay parity tests. There is no change to ordinary frontend world creation.

## Persistence inventory and representation

The completed Phase 17 cutover incremented PostgreSQL schema from **9 to 10** and procedure schema from **1.2 to 1.3**. No additional relational columns are required. A locked, transactional **full-database conversion** adds the validated periodic tiling to every existing world snapshot, preserving each legacy grid as a read-only-compatible projection. All stored campaign procedure revisions and expedition-pinned procedure snapshots advance to schema 1.3 without changing their IDs, revision numbers or D-symbol identity. Hex-only runtime admission compares canonical Euclidean D-symbol identities, so syntactically equivalent saved tiling declarations remain compatible. The existing advisory lock and optimistic aggregate version checks remain unchanged.

**Historical upgrade strategy (completed; implementation archived):** before accepting normal requests, the schema 9→10 migration locked the database, inspects every world, validates its prior grid, constructs its exact polygonal geometry, and writes both a format-2 marker and the periodic witness using JSONB updates that retain every unrelated field. A malformed world, world-snapshot/row ID mismatch, unknown top-level snapshot field, unsupported snapshot version, mismatched existing topology, or unexpected pinned-procedure schema aborts **the entire transaction**, leaving all records on schema 9. The format-2 reader intentionally rejects unrecognized top-level world fields to avoid silently dropping them on later saves. The migration therefore refuses any such format-1 record *before conversion* instead of leaving an unreadable upgraded world; inspect its unknown fields and supply an explicit preserving migration. The migration upgrades every stored procedure schemaVersion 1.2 to 1.3 in `campaign_procedure_revisions` and `expeditions`, with `tilingDsSymbol` unchanged. The transaction records schema 10 only after all conversions succeed. A repeat invocation is a no-op. Existing world and expedition aggregate versions, ownership, timestamps and event sequences do not change solely due to schema migration.

New hex worlds also serialize the generalized tiling plus legacy grid projection, and newly authored nonhex worlds serialize only the tiling. Format-2 snapshots with a legacy grid must pass cross-checks confirming identical physical cell locations and topology, so there is only one authoritative geometry.

**Old/new application coexistence during the completed cutover:** schema 9 applications reject schema 10 during startup, so the original release used a controlled single-writer cutover. The original pre-upgrade PostgreSQL and map-asset backup remains available for disaster recovery, but restoring it requires the archived upgrade implementation (Phase 17 merge `184a2cc0caeb935af450b922561baa10ea7fb612`) or restoration of a matching older application. Do not run current schema-10-only code against a schema-9 backup.

## Completed Phase 17 cutover and current deployment behavior

The dev/testing application reached PostgreSQL schema **10** and passed the deployed `/ready` check after a verified pre-cutover database dump and map-asset backup were restored in isolation. The one-time rollback attestation and deployment gate are no longer part of the active workflow; neither are the schema-8→9 and 9→10 data-conversion methods. Their implementation and tests remain available in Git history at the original Phase 17 merge and subsequent deployment-fix commits.

`PostgresSchemaMigrator` remains the durable application schema framework. It creates the current schema 10 in new databases under the PostgreSQL advisory lock, accepts existing version 10 without mutation, and refuses earlier or unknown versions without modifying saved records. A schema-8/9 database or an old pre-cutover backup must be upgraded by a separately verified historical recovery path; deleting the old live-data upgrade code **does not** grant permission to reset historical databases or to discard the verified backup pair.

The regular deployment retains the prior running image, validates the private runtime configuration, builds and smokes the new container with disposable PostgreSQL, replaces the container, checks the exact image revision and PostgreSQL-backed `/ready` status, and retains private rollback evidence on failed or uncertain deployments. It does not auto-restore or truncate the production/dev database or the map volume. Backup/restore smoke tests remain in CI as a reusable reliability test for future schema upgrades.

Live signed-in verification of saved worlds and map access was reported by the project owner after the Phase 17 deployment. That does not substitute for explicit checks of every existing expedition, map registration, pinned procedure and nonspatial session.

## Phase 18 integration

Introduce cell-based runtime state **additively** with preserved historical axial state during cutover. Define movement distances from actual boundary/route geometry and explicit ambiguous-vertex handling. Prove that old hex traversal, progress, navigation and event history replay unchanged before retiring the hex adapter. Phase 19 should replace legacy hex-only canvas geometry using bounded generalized world polygon enumeration.
